## 1. 何をするツールか

- flow5（低レイノルズ数向けの空力解析ソフト）を、**AI エージェントから叩けるようにする**もの
- 対象は鳥人間コンテストの人力機、RC グライダー、UAV など
- 入口は2つ。**どちらも同じ中身を呼ぶ**ので、片方だけできることは無い

| 入口 | 起動 | 想定利用者 |
|---|---|---|
| MCP サーバ | `flow5ctl mcp` | Claude Desktop、MCP 対応クライアント |
| CLI | `flow5ctl <verb>` | Claude Code、Codex、人、CI |

---

## 2. 4つの層

図の上から順に、依存は必ず下向きです。

| 層 | 中身 | 役割 |
|---|---|---|
| **入口** | `cli` / `mcp_server` | 引数を受け取るだけ。判断はしない |
| **ユースケース** | `analyze` `trim` `sweep` `plot` ほか | 手順を決める。ガードレールを掛け、flow5 を2パスで走らせる |
| **ドメイン** | `model` `geometry` `advisor` `project` `viz` | 幾何と妥当性。**flow5 を一切知らない** |
| **アダプタ** | `xmlgen` `results` `markers` `summary` `runner` `probe` | flow5 の癖を全部ここに閉じ込める |

### なぜこの分け方なのか

**flow5 の癖が多すぎるからです。** 詳細は
[FLOW5-INTERFACE.md](FLOW5-INTERFACE.md) にありますが、たとえば：

- 失敗しても終了コードは `0`（ただしクラッシュ時だけ 139）
- ポーラーの `.csv` にカンマが1つも無い
- 1行目のデータがヘッダ行にくっついている
- `Static margin` の単位はパーセント
- 1つのスクリプトに2種類の解析を書くと**必ず SIGSEGV で落ちる**

こういう知識は、コードとテストに固定するしかありません。
**アダプタ層がその置き場**で、それ以外の層には漏らしません。

## 3. コードで検証した不変条件

図の緑の枠に書いてあるものです。いずれも import グラフを AST で抽出して確認しました。

### ドメインは flow5 を import しない

- `model` / `geometry` / `advisor` / `project` / `viz` から flow5 への import は **0 本**
- だから **flow5 がインストールされていない CI でもテストが全部通る**
- これが崩れると CI が動かなくなるので、事実上テストが番人になっています

### 入口から flow5 に届くのは `probe` だけ

- `cli` と `mcp_server` が flow5 から使うのは **版数検出（`probe`）のみ**
- `doctor` コマンドのためで、解析本体は必ず `usecases` を経由します
- 図の破線がこれです

### 図に描いていないもの

- `errors` は全モジュールが import するので、描くとノイズになるだけ
- ディレクトリ構成そのもの（それはアーキテクチャではありません）

## 4. データの流れ

```
design.yaml  →  geometry で面積・MAC・重心を計算
             →  advisor が妥当性の帯と突き合わせて警告
             →  xmlgen が flow5 の XML を書く
             →  runner が flow5 を2回起動（2パス必須）
             →  results が壊れた CSV を読む
             →  summary が数値に要約
             →  results/<名前>.json に残す
```

- **`build/` は次の解析で消えます。** あとで図を描くのに要るものは `results/` に保存します
- `design.yaml` が唯一の正本。人が読めて、git で差分が取れます

### なぜ2パスなのか

`<foil_analysis>` と `<Plane_analysis>` を1つのスクリプトに書くと flow5 が
**再現性をもって SIGSEGV で落ちる**からです。7通りの構成で切り分けて確認しました
（[ADR-0009](adr/)）。

- 1パス目: 翼型の2次元ポーラーだけを計算
- 2パス目: 3次元解析。1パス目の結果を粘性抗力の補間に使う

## 5. ガードレールという考え方

flow5 は**間違った入力でも、それらしい数字を返してきます**。
このプロジェクトで一番怖いのは落ちることではなく、**もっともらしい嘘**です。

そこで flow5ctl は、疑わしい場合に**警告ではなく拒否**します。

| 状況 | flow5 の挙動 | flow5ctl の挙動 |
|---|---|---|
| T1 極線で安定性を聞く | 固有値 `5.995e+51` を返す | 拒否して T7 を案内 |
| 2Dポーラーの範囲外 | 黙って補間 | どの範囲が足りないか数字で報告 |
| 参照寸法が未指定 | ゼロを返す | 常に `CUSTOM` を明示 |

### 実機と突き合わせて分かったこと

公表三面図から4チーム・6機を再構成して検証しました
（記録は `validation/`、これは gitignore 対象です）。

- 幾何（面積・スパン・MAC・アスペクト比）は誤差 **0.1% 以内**
- **静安定余裕**は公表重心を持つ3機すべてで古典理論と整合
- ただし**抗力の絶対値は 16〜28% 悲観的**。原因は未解決

この過程で、**合成テストでは絶対に見つからない**種類のバグが7件出ています。
「出力が妥当に見えて実は間違っている」ものは、外部の正解が無いと検出できません。

## 6. これから — A2A の見通し

将来的に「空力設計エージェント」を組むとき、分割線をどこに引くかの整理です。

### flow5ctl は単体で完結させる

理由は、これまでに見つかったバグの性質です。フィンが水平に生えていた、
重心高さ項を静安定余裕と混同していた、flow5 の Cn・Cl が教科書と逆符号だった —
これらは**すべて「flow5 という特定のソルバの癖」**に属します。

汎用の設計エージェントがプロンプトで持てる知識ではなく、
**コードとテストとして凝固させるしかない**ものです。

> flow5ctl の価値は「AI が flow5 を叩ける」ことではなく、
> **「flow5 の嘘を知っている」ことがコードになっている**点にあります。

OSS として配るなら、この境界のままが正しいと考えています。

### 分割線は「ソルバ知識」と「設計判断」の間

| 層 | 性質 | 例 |
|---|---|---|
| **ソルバ層**（= flow5ctl） | 決定的・テストで守れる | 幾何を作り、解き、数値を返す。信用できない数値は返さない |
| **知識層** | 非決定的・出典が本質 | 「HPA の V_h は 0.32〜0.44」「DAE 系は Cl 0.85 で遷移が前縁に飛ぶ」 |
| **判断層** | トレードオフを決める | 両者を呼んで設計を進める |

**注意点があります。** ガードレールの帯を実機6機から引き直した作業は、
本来は知識層の仕事です。今は `presets/hpa.yaml` にハードコードしていますが、
これが増えると flow5ctl が設計知識を抱え込み始めます。

境界としては「**ソルバが返す数値の妥当性検査までが flow5ctl、
なぜその帯なのかは知識層**」という線が引けます。

### ただし当面の優先順位は A2A ではない

A2A は「flow5ctl が単体で信用できる」ことが前提です。今の残課題：

1. **Linux / Windows 未検証** — OSS として配るなら最大のリスク
2. **抗力の絶対値が 16〜28% 乖離**（4チーム・3機で再現）
3. **誰も外部で使っていない**

まず抗力の乖離を詰めて、Linux で動くことを確かめて、誰かに使ってもらう。
その順だと考えています。

なお **MCP を選んだこと自体は今も正しい判断**です。A2A になっても
MCP サーバはそのまま「ソルバ層のツール群」として使えます。
